# Save formats and compatibility

The gameplay ruleset remains M01 `4.0.0`. Portable format versions and the snapshot engine compatibility ID are independent of that ruleset. The unchanged GDD Section 16 remains the product authority.

## Format 2

The envelope contains `schemaVersion: 2`, `ruleset`, `runId`, the full accepted `commands`, `revision`, `latestCommittedRevision`, `manifest`, `snapshot`, final `stateHash`, `metadata` and envelope `hash`.

The manifest pins mission `M01`, the deterministic world selection, the canonical fixture checksum and snapshot engine ID `m01-snapshot-2`. The manifest also pins content, rubric, policy, authored-profile and selection-algorithm versions, with a null seed for the finite recorded selection. Unknown versions are incompatible; they never reroll or silently translate the case. The snapshot stores its `throughRevision`, full engine state and gameplay hash. Normal writers prefer the latest state, but use a revision-zero checkpoint plus the full trailing log when the compact full-snapshot envelope exceeds 2 MiB. Explicitly requested boundaries stay exact. If even the minimal envelope exceeds the limit, reject without writing or dropping actions. The reader also supports earlier boundaries with a trailing command slice, covered by tests. Revisions count accepted commands, including free commands; they are separate from simulation ticks.

Snapshot state contains the immutable delivered observations and references, draft, pending requests, internal facts/cache, original receipt ledger, command prefix, history and closed report. These private fields never become a React player projection merely because they are in a save.

## Validation and replay

1. Enforce 2 MiB, 20,000-command and depth-64 bounds, reject unsafe object keys and reserved receipt-map command IDs (`__proto__`, `constructor`, `prototype`), parse strict outer schemas and verify the envelope checksum.
2. Verify content compatibility, revision bounds and snapshot boundary.
3. Independently reconstruct the command prefix and its expected receipt acknowledgements. Compare the complete canonical snapshot, including every nested field, with that audited state. This supplies runtime structural and semantic validation for the nested snapshot; TypeScript assertions alone do not validate it.
4. Clone the validated snapshot. Apply only `commands.slice(throughRevision)` to it, reject duplicate/rejected commands and restore the recorded acknowledgement boundary.
5. Compare final revision and gameplay hash. Absolute pending-check due ticks survive unchanged.

The audit is separate from restoring and advancing the snapshot. It still audits the full prefix. Owned replay clones the supplied checkpoint once and retains private ownership during the audit, avoiding per-command whole-state copies. Browser callers run it in an isolated, preloaded worker to preserve interface responsiveness; command validation and canonical comparisons are retained. Each validation request has a 20-second deadline. A failed worker is terminated and reported as unavailable validation, without changing stored data or treating a healthy row as corrupt. Retry creates a new worker. Non-browser unit/authoring tools retain the pure synchronous reader. Serialization and cloning still use the interface thread.

FNV-1a checksums detect accidental corruption. They are not signatures or protection against an owner editing a local single-player save. Gameplay hashes exclude persistence metadata and normalize receipt durability; the envelope checksum covers those fields too. Export metadata is deterministic, with no new clock timestamp generated by reading or media playback.

## Commit and receipt contract

The pure engine creates accepted `memory_only` receipts. Persistence prepares a separate clone with `committed` receipts and its acknowledged revision, validates it, and writes it transactionally. Only after transaction completion does `commit` return that clone for the controller to expose. Failure never promotes caller receipts or discards accepted in-memory work. Reloading a valid database row establishes its durable revision. Duplicate commands return the original receipt without reapplying the action.

A portable file can contain both previously committed and newer memory-only actions. Those acknowledgements describe the exported history, not a cloud backup or a guarantee that the file is saved in the importing browser. Importing into durable local storage still requires a successful transaction.

## Format 1 and recovery

The legacy envelope contains run ID, world, ruleset, commands and checksum. It is validated and replayed with the retained M01 rules. Reading an old local row does not rewrite it. The next successful commit writes format 2 while retaining the exact old envelope as the previous backup. A failed commit leaves that row untouched. `exportLegacySave` is retained for compatibility fixtures; normal player exports use format 2. Old deployed builds cannot read format 2.

The previous save can be recovered only after validation. Damaged/incompatible records remain available through the raw original export and explicit recovery/restart controls. Recovery archives the most recent original atomically and rejects a changed inspected row. A raw recovery record is an inspection artifact, not a portable save. No automatic migration of future incompatible rulesets or snapshot versions is promised; add explicit compatibility handling and tests when those change.

Storage is browser-origin scoped and can be evicted or cleared. Export before switching devices or deployment hostnames. Physical termination, eviction, private-mode behavior and unsupported-Web-Locks fallback remain release checks.

## Causal-ledger generation and completed cases

`m01-snapshot-2` adds the deterministic seven-phase simulation, authored dependencies, source-origin/collection records, immutable acquisition catalogue and post-close reconstruction. The retained `legacyEngine.ts`/`legacyFormat.ts` reader validates `m01-snapshot-1` envelopes using their original structure and hashes. A deterministic replay with the new engine may add the ledger only if every original state/report/receipt field remains canonically identical; otherwise migration is rejected. Tests cover each world, closed findings, committed receipts and earlier snapshot boundaries. Old local rows are still not rewritten just by reading them.

A completed durable run is archived transactionally before a replay/new case clears the active slot. The archive retains the frozen report and is exportable. Same-world replay uses a new run ID, fresh clock and new finding; it cannot edit the original score. Temporary-session restart preserves the separate durable case. Browser storage remains best-effort, so export archives for an independent backup.

## Asynchronous validation and transaction boundary

All browser reads/imports/commits/recovery/archive paths await the same validator. An initial ready handshake completes before the application advertises case-ready, including when the active slot is empty, so the validator code is already loaded for offline continuation. Worker startup/messaging failure does not trigger an unsafe synchronous browser fallback.

Commit envelope/hash preparation and its semantic audit also run in the worker. Commits and replay archival validate an inspected row outside the database transaction. The transaction then compares the entire current row with that inspected row, in addition to the run/revision checks, before writing. Worker promises never keep a Dexie transaction open. A concurrent replacement at the same revision is rejected. No envelope format, compatibility ID, fixture, command, due tick or rubric changed in this iteration.

When browser validation cannot start for an existing save, offer an explicit raw stored-data recovery export without validating or rewriting it. Keep that recovery copy distinct from portable imports; temporary play must leave the original row unchanged.

The current reader uses `replayCommands` for prefix audits, trailing commands, format-1 reconstruction and additive migration replay. The snapshot-1 reader itself is retained unchanged and can still have the older replay cost. No schema/engine compatibility ID changed: complete reconstructed states are checked against the immutable path.

Portable downloads are compact JSON, measured as UTF-8 against the same 2 MiB reader limit. Browser export preparation runs in the preloaded worker and preserves the exported acknowledgement boundary; exporting temporary progress does not commit receipts. A revision-zero checkpoint changes only representation: the existing format-2 reader audits that checkpoint, applies all trailing commands and verifies the final hash. No schema, fixture, ruleset or engine compatibility ID changes.

## P1 missions — independent envelope and namespace

M04/M07 do not widen or reinterpret M01 saves. Their `threat-hunter-p1` schema-1 envelope and `threat-hunter-campaign-v1` database are separate. Select the matching mission before import. The manifest pins `p1-1`, content 1.0.0, rubric `p1-1.0.0`, mission-specific policy, profile `p1-authored-worlds-1`, fixture hash, private world, null seed and finite selection algorithm. Each active mission has previous-save retention, its own writer lock, completed archives and raw recovery-original storage.

The envelope contains a latest or revision-zero checkpoint, full accepted log, final state hash, acknowledgement boundary and checksum. UTF-8 2 MiB/depth-64/20,000-command limits, unsafe keys, strict schemas, independent prefix audit, exact canonical checkpoint comparison and final reconstruction apply. P1 FNV-1a checksums use canonical UTF-8 bytes; they detect accidental damage and are not authentication. No future ruleset/profile migration is silently accepted.

The preloaded `p1Worker.ts` prepares/audits imports, commits and compact exports with a 20-second request limit. Exports do not commit volatile receipts. Commit validates the inspected old row outside its transaction, compares the whole row again inside, and returns an acknowledged clone only after success. Recovery archives the original before replacement. Failed writes retain accepted memory for export/retry; retry never redispatches commands. Unsupported Web Locks permit read/export and explicitly chosen temporary play, never coordinated writes. Switching loaded mission screens retains volatile work and never merges different journals.

## Nine expansion missions and constrained free hunts

M02/M03/M05/M06/M08/M09/M10/M11/M12 use the independent `threat-hunter-expansion` schema-1 envelope and `threat-hunter-expansion-v1` database. Content 1.0.0, engine `expansion-1`, rubric `expansion-1.0.0`, per-case response policy, fixture hash and profile `expansion-authored-worlds-1` are pinned. `mode`, `seed`, generator and selection algorithm distinguish authored runs from free hunts. The finite `causal-templates-xorshift32-1` generator selects a validated template/world and standard, late-collection or slow-response profile. Import recomputes that selection; it never generates unrelated evidence. Free hunts use their own `active:free` slot and writer lock, independent of an authored run using the same template.

Snapshot/prefix/final-state auditing, original acknowledgement boundaries, 2 MiB UTF-8 limits, strict hostile-input rejection and complete-row transaction comparison follow the existing contracts. `expansionWorker.ts` handles browser audits, exports and commit preparation, with explicit unavailable/retry behavior. No original M01 or P1 reader is reinterpreted.

P1 and expansion active-backup replacement requires explicit player confirmation, validated matching-slot input and a fully durable current run. The transaction preserves the entire original row under a unique `replaced:<slot>:<UUID>` key, retains its envelope as the new previous save, and archives a completed finding before replacing the active slot. Failed validation, stale rows or write failure leave the active row and backups unchanged. Preserved replacement backups remain exportable. Import resets presentation buffers and comparison selections even when the imported run ID matches the old run.

Completed archive keys retain their original identity. If an imported run reuses an existing run ID with different valid history, a unique `:copy:<UUID>` suffix preserves both archives instead of overwriting either. Read-only journey adapters validate the embedded mission/run identity and permit only this exact suffix shape. Completed archives do not constitute cloud backup; export independently before clearing site data.
